## 二、分层依赖方向

```
view ──▶ controller ──▶ service ──▶ repository ──▶ (文件)
              │              │
              └──────────────┴──▶ domain ◀── exception
                                    │
                                  util（被各层调用，不反向依赖任何层）
```

**关键约束（已用 import 检查验证）**：

- `domain` 不依赖任何其它包 —— 它是内核；
- `view` 只依赖 `service` 接口与 `domain`，**不依赖 `repository`**；
- `Controller` 只依赖 `view`、`service`、`domain`、`exception`，**不依赖 `repository`**；
- `util` 被各层调用，但自己不 import 任何业务包（只用 `java.util.logging`）。

## 四、接口签名对照（「不可改一个字符」）

**作业原文**

```java
public interface EntryRepository {
    List<Entry> load() throws StorageException;
    void save(List<Entry> entries) throws StorageException;
}
```

**实际文件** `src/com/accountbook/repository/EntryRepository.java`：签名、方法名、参数、返回类型、`throws` 全部一致；仅额外加了 `import java.util.List;` 与 `import com.accountbook.domain.Entry;`。

```java
public interface AccountBookService {
    void add(Entry entry) throws ValidationException, BusinessException, StorageException;
    void update(Entry entry) throws ValidationException, BusinessException, StorageException;
    void delete(String id) throws BusinessException, StorageException;
    List<Entry> listAll();
    QueryResult search(String keyword, EntryType type);
    void reload() throws StorageException;
}
```

**实际文件** `src/com/accountbook/service/AccountBookService.java`：六个方法与原文逐字一致。

> 注：`delete` 的 `throws` 列表里没有 `ValidationException`，与原文一致 —— 删除不需要校验字段，只可能"不存在"或"存盘失败"。这个细节说明作业的签名是认真设计过的。

## 五、异常体系统照表

| 异常类 | 父类（作业规定） | 实际声明 | 抛出位置 | 触发场景 |
|---|---|---|---|---|
| `BusinessException` | `RuntimeException` | `extends RuntimeException` | Service | id 重复、id 不存在、删除不存在的记录 |
| `ValidationException` | `BusinessException` | `extends BusinessException` | `Entry.validate()`、Controller 解析表单 | 日期空/格式错、类型空、类别空/超长、金额非数字/≤0、备注超长 |
| `StorageException` | `RuntimeException` | `extends RuntimeException` | `FileEntryRepository` | 文件不存在（仅 `save` 时）、IO 失败、CSV 字段数不对、日期/类型/金额解析失败 |

**为什么 `ValidationException` 继承 `BusinessException`**：作业表格明确这么写。副作用是 `catch` 顺序必须是"先子后父"，否则校验错误会被当成业务错误。这条在 `AccountBookController.execute()` 里有注释标明。

## 六、统一异常处理对照（「四、其他设计说明 · 4.基本异常」）

作业要求的三条原则与实现：

| 原则 | 实现 |
|---|---|
| Controller 中捕获 `ValidationException`/`BusinessException` 显示可读提示 | `execute()` 里 `catch (ValidationException e) { view.showInputError(e.getMessage()); }` |
| 捕获 `StorageException` 提示"数据保存/读取失败，请检查文件" | `catch (StorageException e) { LogUtil.error("存储失败", e); view.showError("数据保存或读取失败，请检查 data/entries.csv 是否可写"); }` |
| 其他未预期异常记录日志并提示"系统异常"，**禁止空 catch** | `catch (RuntimeException e) { LogUtil.error("未预期异常", e); view.showError("系统异常：" + e.getMessage()); }` |

**没有一个 catch 块是空的**：安全检查方式 —— 搜 `catch (` 后跟 `{ }` 的空块，结果为 0。

## 九、不符合项

**无。**
