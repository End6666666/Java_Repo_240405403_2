# 04 测试报告

> 配套材料：`03-测试记录.md`（59 个用例清单与运行日志）。本文件第三节收录了三段注入实验的完整原始输出。

---

## 一、测试策略

**分层测，各测各的边界。**

| 层 | 用什么测 | 为什么这么选 |
|---|---|---|
| `domain`（Entry / QueryResult） | 纯 JUnit，无依赖 | 对象自己就能验，不需要文件也不需要界面 |
| `repository`（CSV 读写） | 真实临时文件（`TemporaryFolder`） | 要验的就是"写出去的文件能不能读回来"，换成假对象就没有意义了 |
| `service`（业务逻辑） | 内存 `FakeRepository` | 核心要验"写盘失败必须回滚"，只有能控制 `save()` 抛异常才测得了 |
| `controller` / `view` | 不自动化，冒烟 + 手工 | Swing 事件测试成本高于收益，见第五节 |

**测试优先级**：异常路径 > 边界值 > 正常路径。因为正常路径写代码时就会跑到，异常路径不会。

## 三、注入实验（核心部分）

**目的**：验证"测试真的能发现错误"，而不是"测试跑过了所以代码没问题"。

**方法**：手工把已经修好的代码改坏，看测试是否变红、红的是不是预期那一条，看完立即用 `git checkout` 还原。

### 实验 A：拿掉删除失败的回滚

**注入点**：`src/com/accountbook/service/AccountBookServiceImpl.java` 第 93 行，注释掉这一行

```java
} catch (StorageException e) {
    cache.add(index, removed);   // 这一行就是回滚：把删掉的元素放回原位
    throw e;
}
```

**预期**：`ServiceTest.deleteRollsBackAndKeepsOrder` 变红，其余不动。

**实际**

```
1) deleteRollsBackAndKeepsOrder(com.accountbook.test.ServiceTest)
   java.lang.AssertionError: expected:<3> but was:<2>
Tests run: 19,  Failures: 1
```

**结论**：命中。删掉的是"回滚"这一行，测试立刻发现缓存少了一条。说明这条用例真的在验回滚，不是摆设。

---

### 实验 B：金额取整改回 `Math.round`

**注入点**：`src/com/accountbook/domain/Entry.java` 第 79–81 行的 `round2` 方法

```java
// 修复后的写法（项目里现在的样子）
return BigDecimal.valueOf(value).setScale(2, RoundingMode.HALF_UP).doubleValue();

// 注入的错误版本（修复前的写法）
return Math.round(value * 100.0) / 100.0;
```

**预期**：`EntryTest.round2KeepsTwoDecimals` 变红。

**实际**

```
1) round2KeepsTwoDecimals(com.accountbook.test.EntryTest)
   java.lang.AssertionError: expected:<1.01> but was:<1.0>
Tests run: 23,  Failures: 1
```

**结论**：命中。

**但有个值得记的细节**：`QueryResultTest.decimalSumDoesNotDrift`（0.1 + 0.2 == 0.3）**仍然是绿的**。因为 0.1+0.2 = 0.30000000000000004，×100 = 30.000000000000004，`Math.round` 也得 30 —— 这个用例根本测不出 `Math.round` 的精度问题。

真正能测出来的是 `1.005` 这种"恰好卡在 .xx5"的值。

**这揭示了测试的一个本质**：同一类问题，不同用例的覆盖力差别很大。写了 10 个"看起来在测精度"的用例，可能一个都测不到点子上。

---

### 实验 C：取消 CSV 跨行拼接

**注入点**：`src/com/accountbook/repository/FileEntryRepository.java` 第 122 行

```java
private static boolean isQuoteBalanced(CharSequence text) {
    ...
    return true;   // 注入版本：原来是 return quotes % 2 == 0;
}
```

**预期**：`RepositoryTest.newlineInsideNoteSurvivesRoundTrip` 变红。

**实际**

```
1) newlineInsideNoteSurvivesRoundTrip(com.accountbook.test.RepositoryTest)
   com.accountbook.exception.StorageException: 账本文件第 1 行损坏：双引号未闭合
Tests run: 17,  Failures: 1
```

**结论**：命中。异常类型和消息都和当初手工复现时一模一样。

---

### 三段注入的汇总

| 实验 | 注入点 | 变红的用例 | 失败数 | 是否命中 |
|---|---|---|---|---|
| A | 删除回滚行 | `deleteRollsBackAndKeepsOrder` | 1 / 19 | 命中 |
| B | `Math.round` | `round2KeepsTwoDecimals` | 1 / 23 | 命中 |
| C | 取消跨行拼接 | `newlineInsideNoteSurvivesRoundTrip` | 1 / 17 | 命中 |

三次都是**只红 1 条**。这说明每个用例盯的就是一件事，没有出现"一处坏、一片红"的糊成一团——测试的**定位精度是够的**。

每次注入后都已还原，最终 `git status` 干净，全量 `OK (59 tests)`。

**实验环境与还原方式**

- JDK 25.0.4.1、JUnit 4.13.2，注入前的基线为 `OK (59 tests)`
- 还原命令：`git checkout -- src/com/accountbook/domain/Entry.java src/com/accountbook/repository/FileEntryRepository.java src/com/accountbook/service/AccountBookServiceImpl.java`
- **别用复制备份的方式还原**：实验中途试过用 `cp` 备份覆盖回去，结果 `import` 之间少了一个空行，`git diff` 多出一条删除。`git checkout` 才是干净的。

**关于"结论"这一栏**：上面每段的结论是我事后的判断。做实验时我记的是"我预期什么、实际是什么"，两者的差距才是这次实验真正的收获。

## 五、未覆盖的部分与理由

| 未覆盖 | 理由 | 替代手段 |
|---|---|---|
| `MainFrame` 的 UI 细节 | 无头环境跑 Swing 不稳定；断言"按钮在不在"价值低 | 手工点测 |
| `AccountBookController` 的事件分发 | 要用 `invokeAndWait` 驱动事件队列，测试代码量超过被测代码 | 冒烟程序 + 手工点测 |
| `LogUtil` 的输出内容 | 断言日志文本很脆（改一个字就红），收益低 | 人工看 `logs/app.log` |
| 并发场景 | 作业明确不做多线程 | — |
| 大数据量性能 | 个人记账场景，几千条足够 | — |

**取舍说明**：作业要求"JUnit4 覆盖正常、边界、异常"，59 个用例在领域、持久化、业务三层已经覆盖完整。Controller 与 View 是"胶水层"，它们的正确性靠界面点测更直接。

## 六、结论

1. **测试确实抓到了一个真 bug**（`Math.round` 精度），但**只抓到一个**——其余四个问题都是我读代码、点界面、设计用例时想到的。
2. **注入实验证明测试是有效的**：三处注入三处变红，且都精准定位到单条用例。
3. **测试有盲区**：`decimalSumDoesNotDrift` 这种"看起来在测精度"的用例，实际上测不出精度问题。用例写得对不对，比写多少个更重要。
4. **界面层没测**是明确取舍，不是遗漏。但代价是问题 2（表格排序取错行）只能靠手工发现——如果那个 bug 没被点到，就会一直留在代码里。
