## 二、领域对象

### 2.1 Entry（记账记录，轻量富领域对象）

| 字段 | 类型 | 含义 | 约束 |
|---|---|---|---|
| `id` | `String` | 记录唯一标识 | 非空；新增时由 Service 生成，不由 View 填 |
| `date` | `LocalDate` | 发生日期 | 非空，格式 `yyyy-MM-dd` |
| `type` | `EntryType` | 收入 / 支出 | 非空 |
| `category` | `String` | 类别（餐饮、工资…） | 非空，去首尾空白后不得为空串 |
| `amount` | `double` | 金额 | `> 0`，且为有限数（非 NaN / 非 Infinity） |
| `note` | `String` | 备注 | 可为空；长度 ≤ 100 |

方法：`validate()` —— 只做**单条记录自身**的字段校验，不通过则抛 `ValidationException`。

> 职责边界：`Entry` **不**知道余额、不知道汇总，也**不**负责读写文件。

### 2.2 EntryType（枚举）

```java
INCOME, EXPENSE
```

- 只做类型标识，不携带行为。
- 保存到文本时用 `name()`（`INCOME` / `EXPENSE`），读回时用 `valueOf` 并捕获 `IllegalArgumentException` 转成 `StorageException`（文件被手改坏时不能崩）。

### 2.3 QueryResult（查询结果对象）

| 字段 | 类型 | 说明 |
|---|---|---|
| `entries` | `List<Entry>` | 命中的**完整明细** |
| `totalIncome` | `double` | 命中集合的收入合计 |
| `totalExpense` | `double` | 命中集合的支出合计 |
| `balance` | `double` | `totalIncome - totalExpense` |
| `count` | `int` | `entries.size()` |

- 无参构造 `QueryResult()`，由 `AccountBookService` 在查询后填充。
- 三个汇总值都是**派生量**，由 `entries` 算出，**不落盘、不缓存在 Entry 里**。

## 三、余额到底放哪一层（审查要点①）

三种候选，我倾向 C：

| 方案 | 位置 | 问题 |
|---|---|---|
| A | `Entry` 里加 `balance` 字段 | ❌ 一条流水没有"余额"概念；一旦删除中间记录，历史余额全错；还得为它设计重算逻辑 |
| B | Service 里用 `double` 成员变量缓存 | ⚠️ 能跑，但状态分散、`reload` 后易忘记刷新，且查询条件变化后"余额"定义就模糊了 |
| C | `QueryResult.balance`，从命中明细现算 | ✅ 纯函数式派生，无状态残留；查询条件不同，余额自然对应"这批记录"的净额 |

> ⚠️ 需你确认的语义：`balance` 是**当前查询结果集的净额**，还是**全账本总余额**？作业原文写"余额、收入合计、支出合计放 QueryResult，由 Service 计算"，按字面理解是前者。若老师要求"账户总余额"，则应新增 `getTotalBalance()` 走全量查询，不走 `search`。

## 四、充血还是贫血（审查要点②）

当前设计：**轻量充血**（thin rich domain）。

- 充血的部分：`Entry.validate()` 把"字段本身是否合法"收在实体内部，View/Service 不重复写一遍判空。
- 贫血的部分：跨记录规则（id 不存在、id 重复、业务状态不允许）**不**放进 Entry —— Entry 看不到其他记录，硬塞就得把它和仓储耦合。

判断依据：作业边界设计里明确"Entry 只为**轻量领域对象**，提供 `validate()` 做基础校验；**跨记录**业务规则（如 ID 不存在）由 Service 处理"。所以这条是照要求执行的，不算我自作主张。

## 六、我主动标出的 5 个可疑设计（供你判断，不必全采纳）

作业要求"至少找出 3 处 AI 不合理设计"，这里我给 5 个真实存在的争议点，**你判断哪些确实不合理**：

1. **`amount` 用 `double`** —— 金额用浮点会有精度误差（`0.1+0.2`），严格账务应用 `BigDecimal`。但接口签名已被作业钉死为 `double`，只能妥协；建议在报告"已知局限"里写明，并在汇总时用 `Math.round(x*100)/100.0` 规整到分。
2. **`id` 用 `String`** —— 比 `int` 自增灵活（可直接用 `UUID` 前 8 位），但用户在界面上要手输 id 来做修改/删除，长 id 体验差。可考虑 `String` 但由系统生成、界面只允许"选中表格行"来定位，不让人手打。
3. **`category` 用自由 `String`** —— 灵活但会脏数据（"吃饭"/"餐饮"/"午餐"并存，按类别查询就失效）。建议界面给下拉框固定候选，模型层仍收 `String`。
4. **`Entry.validate()` 抛受检还是非受检异常** —— 三个自定义异常都落在 `RuntimeException` 体系下（`BusinessException`、`StorageException` 直接继承；`ValidationException` 的父类是 `BusinessException`，间接继承），并说"接口保留 throws 用于表达契约"。那么 `validate()` 声明 `throws ValidationException` 只是**文档性契约**，编译器不强制。这点容易在评审时被质疑"throws 是摆设"，需要在报告里解释清楚。
5. **`QueryResult` 无参构造 + setter 填充** —— 可变对象，构造完可能处于"半初始化"状态。更稳的是构造器一次性传入全部字段；但作业类清单写的是 `+QueryResult()`，暂按作业来。

## 八、落盘字段映射（供 02 数据格式章节引用）

```
id,date,type,category,amount,note
20261120-093012-001,2026-11-20,EXPENSE,餐饮,28.50,午饭
```

- 分隔符 `,`；`note` 含 `,` 或换行时用双引号包裹，内部 `"` 转义为 `""`（与 CSV 一致）。
- 首行是否写表头：**不写**，靠列序固定。理由：读文件时少一次"首行是数据还是表头"的判断，避免用户手删表头导致错行。
