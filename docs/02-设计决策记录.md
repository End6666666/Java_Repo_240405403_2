## 决策 1：持久化格式用 CSV

**背景**：作业要求"简单文本/CSV 即可，一行一条记录，不用数据库"。

**选项**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. CSV（逗号分隔） | 一行一条，Excel 能直接打开，好检查 | 备注里含逗号/引号/换行要做转义 |
| B. 自定义分隔符（如 `\|`） | 转义压力小 | 备注里一旦有 `\|` 同样要转义，只是把问题推给别人 |
| C. Properties / JSON | 不用手写解析 | 一行一条的对应关系没了，且要么引入依赖要么自己写解析器 |

**选择**：A，CSV。字段顺序 `id,date,type,category,amount,note`，无表头。

**理由**
- "一行一条"是最直观的心智模型，出问题时用记事本打开就能定位到第几行坏了；
- 有表头反而要多处理一行，且作业没要求；
- 转义虽然要写，但 CSV 的转义规则是公开标准（RFC 4180），不是自创。

**代价**：必须手写 CSV 解析状态机（不能用 `split(",")`），见决策 5。

## 决策 2：余额放在 `QueryResult` 里现算

**背景**：`balance`（余额）到底属于谁？A 版的三个选项。

**选项**

| 方案 | 问题 |
|---|---|
| A. 作为 `Entry` 的字段 | **错**。余额是"截至某时点的累计"，挂在单条记录上，历史记录的余额会随着后续新增而变化，但存下来的数字不会变，导致数据自相矛盾 |
| B. `Service` 的成员变量，增删改时维护 | 能对，但每次增删改都要记得同步；`reload()`、查询过滤时容易漏，一个漏点就永久错 |
| C. `QueryResult` 里由明细现算 | 没有"需要同步"的状态，算一次对一次 |

**选择**：C。

**理由**：**余额不是存储的事实，是计算的结果**。凡是"能算出来"的，就不要"存下来"，否则就有了两个真相，迟早打架。

**代价**：每次查询都要遍历一遍算汇总，O(n)。但查询本来就要遍历筛选，不增加量级。

## 决策 3：校验规则按"单条 / 跨条"切分

**背景**：`validate()` 该管多少？

**选项**

| 方案 | 说明 |
|---|---|
| A. 全塞进 `Entry.validate()` | 包括"id 是否重复" —— 但实体看不到全集，只能靠 `Entry` 持有仓储引用 |
| B. 全放 `Service` | `Entry` 退化成纯数据袋，任何地方都能造出非法对象 |
| C. 按边界切：字段级留实体，跨记录归 Service | 需要约定边界，但两边职责都清晰 |

**选择**：C。

**理由**
- 字段级校验（非空、长度、数值范围）只需要看自己，放 `Entry`，对象一造出来就能自检；
- 跨记录校验（id 重复、id 是否存在）需要看全集，放 `Service`；
- 边界一句话能说清：**"只看得见自己的规则"归实体，"要看得见别人的规则"归 Service**。

**代价**：调用方要知道"哪些错抛 `ValidationException`、哪些抛 `BusinessException`"。缓解方式是 Controller 里两个都 catch，分别提示。

## 决策 4：`ValidationException` 继承 `BusinessException`

**背景**：三个自定义异常的继承关系。

**选项**

| 方案 | 说明 |
|---|---|
| A. 三个都直接 `extends RuntimeException` | 语义上最平，但作业的异常表不是这么写的 |
| B. `ValidationException extends BusinessException`，`StorageException extends RuntimeException` | 作业表格原文 |

**选择**：B（照作业）。

**理由**：作业的表格是评分依据，不按它写就是错。而且语义上讲得通：校验失败也是一种"业务上不允许"。

**代价（重要）**：`catch` 顺序必须先 `ValidationException` 再 `BusinessException`。写反了，校验错误会被当成普通业务错误提示，用户看到的文案从"日期格式不对"变成"操作不被允许"——不崩，但提示没用了。

这个坑在 `AccountBookController.execute()` 里有注释标记，也写进了 `03-问题清单.md` 第 1 条。

## 决策 5：`save()` 先写临时文件再原子替换

**背景**：整份覆盖写盘，如果写到一半崩了会怎样？

**选项**

| 方案 | 风险 |
|---|---|
| A. 直接 `Files.write(target, lines)` | 写到一半断电或异常，原文件被截断，**整本账本丢失** |
| B. 写临时文件再 `Files.move(tmp, target, REPLACE_EXISTING, ATOMIC_MOVE)` | 要么旧文件完好，要么新文件完整，没有中间态 |
| C. 每条记录追加写 | 修改和删除没法做（要重写整个文件） |

**选择**：B。

**理由**：账本数据是"用户唯一一份"，丢了没法恢复。原子替换的成本只是多一次 `move`，收益是"永不会出现半个文件"。

**代价**
- 需要处理 `AtomicMoveNotSupportedException`（某些文件系统不支持），退化成普通覆盖；
- 临时文件如果 `move` 失败会残留，需要 `finally` 里清理并 `LogUtil.warn`。

## 决策 6：`load()` 遇到文件不存在返回空列表，其余错误照抛

**背景**：第一次启动时账本文件不存在，`load()` 该怎么办？

**选项**

| 方案 | 后果 |
|---|---|
| A. 一律返回空列表 | 把"文件损坏/无权限"也当成"空账本"，用户接着录入，下一次 `save()` **覆盖掉原数据** |
| B. 一律抛 `StorageException` | 第一次启动就报错，用户以为程序坏了 |
| C. 只对"文件不存在"返回空，其他 IO 错误/格式损坏照抛 | 区分"还没有账本"和"账本读不了" |

**选择**：C。

**理由**：这两种情况对用户的意义完全不同——"还没有账本"是正常的，"账本读不了"是危险信号。混在一起，最坏的结果是**用空数据覆盖掉真实数据**。

**代价**：`load()` 要区分异常类型。实现上用 `Files.exists()` 先判断，再 `readAllLines`，外层再兜一次 `NoSuchFileException`（因为 `exists()` 和 `read()` 之间有窗口期，文件可能刚好被删）。

## 决策 7：id 用"毫秒时间戳 + 冲突兜底"

**背景**：`id` 是 `String`，由谁生成、怎么生成？

**选项**

| 方案 | 缺点 |
|---|---|
| A. 用户手输 | 体验差，容易输重复、输空 |
| B. `UUID.randomUUID()` | 36 个字符，表格里显示不下，且不可读 |
| C. 自增序号（1,2,3…） | 删除后要维护计数器，`reload()` 后计数器要从文件里恢复，容易错 |
| D. `"E" + System.currentTimeMillis()` | 可读、单调递增、不用维护计数器；同一毫秒内连续新增会冲突 |

**选择**：D，冲突时 `while` 递增兜底。

**理由**：在"单人本地记账"这个场景下，同毫秒冲突的概率极低，加个 `while` 兜底就够。可读性比 UUID 好得多，用户在表格里能一眼看出录入顺序。

**代价**：这就是一个**将就**的方案。如果将来要多端同步，时间戳会撞车。真要改，改 `nextId()` 一个方法就行，不影响其它层。

## 决策 8：查询在 Service 里遍历，不在 Repository 里做

**背景**：`search(keyword, type)` 的过滤逻辑放哪？

**选项**

| 方案 | 问题 |
|---|---|
| A. Repository 里做过滤（传条件进去） | 接口签名被作业钉死，`load()` 不带参数，做不了 |
| B. Service 遍历内存缓存 | 符合"ArrayList 内存缓存"的设定 |

**选择**：B。

**理由**：作业的 Repository 接口只有 `load()/save()`，天生不支持条件查询。而且内存里就是 `ArrayList`，遍历本来就是 O(n)，没必要绕。

**代价**：数据量大时（比如几万条）每次搜索都全扫一遍，界面会卡。当前场景（个人记账）可接受。

## 决策 9：`ServiceTest` 用内存替身，`RepositoryTest` 用真实文件

**背景**：测试 Service 时，要不要用真的 `FileEntryRepository`？

**选项**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 用真实文件 | 更接近生产 | 每条测试要建临时目录、清理；一条写坏会影响别的用例；**没法模拟"存盘失败"** |
| B. 用内存 `FakeRepository` | 快、互不污染、能按需让 `save()` 抛异常 | 需要多写 20 行假实现 |
| C. 用 Mockito | 不用手写 | 作业没要求引入测试框架依赖，且多一个 jar |

**选择**：B（Service 用替身）+ 真实文件（Repository 单独测）。两层各测各的。

**理由**：`Service` 的核心逻辑里有一块是"**写盘失败必须回滚缓存**"，这个场景只有能控制 `save()` 是否抛异常才测得了。真实文件做不到"让它失败"，除非改权限——那既慢又不可靠。

`Repository` 的 CSV 读写则必须用真实文件，因为要验证的就是"写出去的文件能不能读回来"。

**代价**：`FakeRepository` 是手写的，它自己的行为如果写错，测试会"假绿"。缓解方式：`FakeRepository` 的 `save()` 只做 `stored.clear(); stored.addAll(entries);` 两行，简单到不容易错。

## 决策 10：查询后整表重建，不做增量更新

**背景**：新增/修改/删除后，界面表格怎么刷新？

**选项**

| 方案 | 说明 |
|---|---|
| A. 每次 `setRowCount(0)` 后整表重填 | 简单，一定有正确答案 |
| B. 只改受影响的那一行 | 快，但新增/删除要处理行号偏移，搜索有过滤时更复杂 |

**选择**：A。

**理由**：个人记账本的数据量在几百到几千条，整表重填的耗时在毫秒级，用户感知不到。而 B 方案要维护"查询结果 ↔ 表格行"的映射，一处算错就显示错行。

**代价**：表格有排序（点了列头）时，重建后排序状态会重置。这是已知的小瑕疵，接受。

## 附：被否决但值得记一笔的方案

| 方案 | 为什么否决 |
|---|---|
| `Entry` 里存 `balance` | 见决策 2，会导致历史记录的余额与事实矛盾 |
| 用 `split(",")` 解析 CSV | 备注里一个逗号就把字段错位，且不报错——静默错误最危险 |
| 三个异常都直接继承 `RuntimeException` | 与作业异常表冲突 |
| `QueryResult` 提供全套 setter | 汇总可被外部篡改，见 `01-修订说明.md` 第 2 处 |
| `Math.round(x*100)/100.0` 做金额取整 | `1.005` 会算成 1.00，见 `01-修订说明.md` 第 3 处 |
