## 问题 1：`catch` 顺序反了，校验错误被当成业务错误

**代码片段**（AI 生成的第一版 `AccountBookController.execute()`）

```java
} catch (BusinessException e) {
    view.showWarning(e.getMessage());
} catch (ValidationException e) {
    view.showInputError(e.getMessage());
}
```

**问题**

`ValidationException extends BusinessException`（作业异常表就是这么定的）。Java 的 `catch` 按书写顺序匹配，第一条 `catch (BusinessException)` 会把所有 `ValidationException` 一并吞掉，第二条永远进不去。

编译器**不会报错**——因为子类在前、父类在后才是错的顺序，这里是父类在前，语法合法。所以这个 bug 能顺利编译、能跑，只是提示文案错了。

**表现**：用户把日期输成 `2026-13-45`，本该提示"日期格式不正确"，实际弹的是"操作失败：日期格式不正确"（业务错误样式）。不崩，但用户不知道该改哪。

**修复方式**

```java
} catch (ValidationException e) {   // 子类在前
    view.showInputError(e.getMessage());
} catch (BusinessException e) {     // 父类在后
    view.showWarning(e.getMessage());
} catch (StorageException e) {
    view.showError("数据保存/读取失败：" + e.getMessage());
} catch (RuntimeException e) {
    LogUtil.error("未预期异常", e);
    view.showError("系统异常，请稍后重试");
}
```

同时在方法上方加了注释，说明"这里顺序不能调，Validation 是 Business 的子类"。

**修复后测试结果**

Controller 没有 JUnit 覆盖（Swing 事件，见 `04-测试报告.md` 的取舍说明），靠手工验证：

| 操作 | 修复前提示 | 修复后提示 |
|---|---|---|
| 日期输入 `2026-13-45` 点新增 | 操作失败：日期格式不正确 | 日期格式不正确 |
| 金额输入 `abc` 点新增 | 操作失败：金额必须是数字 | 金额必须是数字 |
| 删除不存在的记录 | 记录不存在 | 记录不存在（未受影响） |

## 问题 2：表格排序后，选中行取错了数据

**代码片段**（AI 生成的第一版 `MainFrame`）

```java
int row = table.getSelectedRow();
String id = (String) tableModel.getValueAt(row, 0);
```

**问题**

表格开了 `setAutoCreateRowSorter(true)`。开了排序器之后，`table.getSelectedRow()` 返回的是**视图行号**（屏幕上看到的第几行），而 `tableModel.getValueAt()` 要的是**模型行号**（数据原始顺序的第几行）。

两者只在"没有点过列头排序"时才相等。一旦用户点了"金额"列排序，再选中某行，取到的就是另一条记录。

**表现**：三条记录（10 元、50 元、30 元），按金额降序排，选中第一行（50 元）点删除——实际删掉的是模型里第 1 条（10 元）。**数据静默丢失，且用户以为自己删对了。**

**修复方式**

```java
int viewRow = table.getSelectedRow();
int modelRow = table.convertRowIndexToModel(viewRow);   // 关键
String id = (String) tableModel.getValueAt(modelRow, 0);
```

两处都改了：`getSelectedEntryId()`（删除/修改用）和 `fillFormFromRow()`（点行回填表单用）。

**修复后测试结果**

手工验证（同样没有自动化覆盖）：

| 步骤 | 修复前 | 修复后 |
|---|---|---|
| 录入 10 / 50 / 30 三条 | — | — |
| 点"金额"列头，降序 | — | — |
| 选中第一行（50）→ 删除 | 10 元那条消失 | 50 元那条消失 ✓ |
| 选中第一行 → 点表单回填 | 显示 10 元的数据 | 显示 50 元的数据 ✓ |

## 问题 3：金额取整用 `Math.round`，1.005 变成 1.00

**代码片段**（AI 生成）

```java
public static double round2(double value) {
    return Math.round(value * 100.0) / 100.0;
}
```

**问题**

`1.005` 在 double 里实际存的是 `1.00499999999999989...`。乘以 100 得到 `100.49999999999999`，`Math.round` 取整成 `100`，除以 100 得 `1.00`。

直觉上"四舍五入到两位"，结果少了 0.01。更麻烦的是：这个错误只在**恰好落在 x.xx5 的值**上出现，日常测试几乎碰不到，属于"能跑但偶尔错"的隐蔽 bug。

**修复方式**

```java
public static double round2(double value) {
    return BigDecimal.valueOf(value)
            .setScale(2, RoundingMode.HALF_UP)
            .doubleValue();
}
```

`BigDecimal.valueOf(double)` 走的是 `Double.toString` 的十进制表示（得到 "1.005"），再做 `HALF_UP` 才是人类预期的四舍五入。

**修复后测试结果**

这条是**唯一由测试直接抓出来的 bug**：

```
1) round2KeepsTwoDecimals(com.accountbook.test.EntryTest)
   java.lang.AssertionError: expected:<1.01> but was:<1.0>
Tests run: 15,  Failures: 1
```

改为 BigDecimal 后：

```
OK (59 tests)
```

## 问题 4：备注含换行时，写得进、读不回

**代码片段**（AI 生成的 `FileEntryRepository`，修复前的 `load()`）

```java
List<String> lines = Files.readAllLines(file, StandardCharsets.UTF_8);
for (int i = 0; i < lines.size(); i++) {
    if (lines.get(i).trim().isEmpty()) continue;
    result.add(parseLine(lines.get(i)));   // 一行 = 一条记录
}
```

**问题**

`save()` 时，备注里如果有换行，`escape()` 会用双引号把它包起来，写出这样的内容：

```
E1,2026-11-21,EXPENSE,餐饮,25.5,"第一行
第二行"
```

这在 CSV 规范里是**合法的**（引号内允许换行）。但 `load()` 按 `readAllLines` 逐行读，会把它拆成两行，第一行的引号没闭合 →

```
com.accountbook.exception.StorageException: 账本文件第 1 行损坏：双引号未闭合
```

**整本账本读不出来**。更糟的是：写是成功的，文件已经坏了，用户下次打开软件发现所有数据都没了。

这个 bug 是**写测试时设计用例才想到的**——前面所有测试备注都只有一行。

**修复方式**

`load()` 不再"一行一条"，改成先按引号奇偶把物理行拼成逻辑记录，再解析：

```java
private static boolean isQuoteBalanced(CharSequence text) {
    int quotes = 0;
    for (int i = 0; i < text.length(); i++) {
        if (text.charAt(i) == '"') quotes++;
    }
    return quotes % 2 == 0;
}
```

主循环里：当前行引号不平衡，就把下一行接上继续看，直到平衡；拼接后的整段再交给 `parseLine`，行号仍按**起始物理行**报。

**修复后测试结果**

补了用例 `RepositoryTest.newlineInsideNoteSurvivesRoundTrip`：

```
OK (59 tests)   // 含该用例，Round-trip 通过
```

并且做了注入验证（见 `04-测试报告.md` 第三节的实验 C）：把 `isQuoteBalanced` 改成 `return true;`，该用例立刻变红：

```
1) newlineInsideNoteSurvivesRoundTrip(com.accountbook.test.RepositoryTest)
   com.accountbook.exception.StorageException: 账本文件第 1 行损坏：双引号未闭合
Tests run: 17,  Failures: 1
```

说明这条测试确实盯住了这个修复点。

## 问题 5：`LogUtil` 少了单参 `error()`，Controller 编译不过

**代码片段**（AI 生成的 `LogUtil`）

```java
public static void info(String message) { ... }
public static void warn(String message) { ... }
public static void error(String message, Throwable throwable) { ... }   // 只有双参
```

**问题**

Controller 里统一异常处理时，有些地方只想记一句话（异常本身已经单独记过了），就写了：

```java
LogUtil.error("删除记录失败，id=" + id);
```

编译报错：

```
错误: 无法将类 LogUtil 中的方法 error 应用到给定类型;
  需要: String,Throwable
  找到: String
```

**修复方式**

补一个重载：

```java
public static void error(String message) {
    error(message, null);
}
```

**修复后测试结果**

`javac` 通过，`OK (59 tests)`。
