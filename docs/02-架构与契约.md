## 一、分层与依赖方向

```
View(MainFrame)  →  Controller(AccountBookController)  →  Service(AccountBookServiceImpl)
                                                                   ↓
                                                          Repository(FileEntryRepository) → 文件
                                                                   ↓
                                                          Domain(Entry / EntryType / QueryResult)
```

**依赖只允许向下**：

| 层 | 可以做 | **禁止** |
|---|---|---|
| view | 摆控件、读输入、显示表格与提示 | 读文件、调 Repository、写业务规则 |
| controller | 绑事件、调 Service、捕获异常、刷新 View | 写业务校验、直接操作文件 |
| service | 校验编排、缓存 CRUD、汇总计算、调 Repository、记日志 | 弹窗、Swing API、直接拼文件 |
| repository | 文件读写、格式转换、IO 异常包装 | 业务校验、Swing |
| exception | 只定义类型与消息 | 吞异常、打印后不抛 |
| util | 日志封装 | 持有业务知识 |

## 三、接口签名（照作业原文，不改一个字符）

```java
public interface EntryRepository {
    //从文件中加载
    List<Entry> load() throws StorageException;

    //保存至文件
    void save(List<Entry> entries) throws StorageException;
}

public interface AccountBookService {
    void add(Entry entry) throws ValidationException, BusinessException, StorageException;
    void update(Entry entry) throws ValidationException, BusinessException, StorageException;
    void delete(String id) throws BusinessException, StorageException;
    List<Entry> listAll();
    QueryResult search(String keyword, EntryType type);
    void reload() throws StorageException;
}
```

**契约解读（评审时容易问的点）**：

1. 三个异常都继承 `RuntimeException` 体系，`throws` 子句在 Java 里**不强制**编译期处理，它的作用是**声明契约**——告诉调用方"我可能按这几类失败"。不要在实现里 catch 后静默。
2. `search` 与 `listAll` 不声明 `StorageException`，因为**只读内存缓存**，不碰文件。若查询时缓存是空的、而账本文件有内容，说明 `reload` 没被正确调用——这是 bug，不是正常路径。
3. `delete(String id)` 只收 id，说明删除是"按 id 定位"，不需要整个 Entry。

## 四、异常体系（这里有个坑）

```java
BusinessException   extends RuntimeException      // ID 不存在、重复删除、业务状态不允许 → Service 抛
ValidationException extends BusinessException     // 日期为空/格式错、类型为空、类别为空、金额<=0、备注超长 → Entry.validate 或 Service 抛
StorageException    extends RuntimeException      // 文件不存在、IO 失败、保存失败、文件格式损坏 → FileEntryRepository 抛
```

⚠️ **catch 顺序陷阱**：`ValidationException` 是 `BusinessException` 的**子类**。Controller 里若先写 `catch (BusinessException e)`，所有校验错误都会被当成业务错误，提示语就变成"该记录不存在"这种驴唇不对马嘴的话。

正确写法（必须按此顺序）：

```java
try {
    service.add(entry);
} catch (ValidationException e) {
    view.showMessage(e.getMessage());          // 定位到具体输入项
} catch (BusinessException e) {
    view.showMessage(e.getMessage());          // 业务性提示
} catch (StorageException e) {
    view.showMessage("数据保存/读取失败，请检查文件");
    LogUtil.error("存储失败", e);
} catch (RuntimeException e) {                  // 兜底，禁止空 catch
    view.showMessage("系统异常");
    LogUtil.error("未预期异常", e);
}
```

**统一原则**（作业原文）：① Controller 捕获 `ValidationException` / `BusinessException` 显示可读提示；② 捕获 `StorageException` 显示"数据保存/读取失败，请检查文件"；③ 其他未预期异常写日志并提示"系统异常"。**禁止空 catch**。

## 五、数据格式契约（CSV，一行一条）

```
id,date,type,category,amount,note
```

- **不写表头**。理由：少一次"首行是数据还是表头"的判断，用户手改文件时不会因为删表头导致错行。
- 编码 UTF-8；换行兼容 `\r\n` 与 `\n`（读入时 `stripTrailing`）。
- 转义：字段含 `,`、`"`、换行时用双引号包裹，内部 `"` 写成 `""`。读入用状态机解析，不能用 `split(",")`——`split` 遇到 `"a,b"` 就散架。
- `type` 存 `INCOME` / `EXPENSE`；读回时 `valueOf` 失败 → 抛 `StorageException("文件内容格式损坏")`。
- `date` 存 `yyyy-MM-dd`；解析失败同样算格式损坏。
- 数值规整：写出时 `String.format("%.2f", amount)`，读入 `Double.parseDouble`。

**文件不存在的处理（需要你拍板）**：异常表把"文件不存在"列为 `StorageException` 的触发场景，但**首次运行**没有文件是正常情况。我的方案是：`FileEntryRepository.load()` 严格抛 `StorageException` 以遵守契约；`AccountBookServiceImpl.reload()` 捕获后判断"是否为首次运行"（文件不存在 + 目录可写），降级为空账本并 `LogUtil.warn`。这样契约和体验都不破。

## 六、类清单与关键方法

| 类/接口 | 层 | 职责 | 关键方法/字段 |
|---|---|---|---|
| `Entry` | domain | 单条账记录，轻量富领域 | `validate()`、6 个字段 getter/setter |
| `EntryType` | domain | 收支枚举 | `INCOME`, `EXPENSE` |
| `QueryResult` | domain | 查询结果与汇总 | `entries`、`totalIncome`、`totalExpense`、`balance`、`count` |
| `EntryRepository` | repository | 持久化抽象 | `load()`、`save(List<Entry>)` |
| `FileEntryRepository` | repository | 文本/CSV 读写 | 构造 `File`、`load`/`save`、包装 `StorageException` |
| `AccountBookService` | service | 业务接口 | `add/update/delete/listAll/search/reload` |
| `AccountBookServiceImpl` | service | `ArrayList` 缓存、CRUD、校验编排、汇总、日志、保存 | `List<Entry> cache`、`EntryRepository repo` |
| `AccountBookController` | controller | 事件协调、异常处理、刷新视图 | `onAdd/onUpdate/onDelete/onSearch/refreshTable` |
| `MainFrame` | view | Swing 界面 | `JTable`、`JTextField`、`JComboBox`、`JButton`、`setTableData`、`showMessage`、`addXxxListener` |
| `BusinessException` | exception | 业务异常 | 消息构造器 |
| `ValidationException` | exception | 输入校验异常 | 消息构造器 |
| `StorageException` | exception | 文件读写异常 | 消息构造器 + `(String, Throwable)` |
| `LogUtil` | util | 日志封装 | `info/warn/error`，控制台 + `logs/app.log` |
| `EntryTest` / `ServiceTest` / `RepositoryTest` | test | JUnit4 正常/边界/异常 | `assertThrows` 验证三类异常 |

**Service 内部算法**：

- `add`：`entry.validate()` → 生成 id（若为空）→ 查缓存判重 → 加缓存 → `repo.save(cache)` → 失败则回滚缓存并抛 `StorageException`
- `update`：`entry.validate()` → 按 id 找位置 → 不存在抛 `BusinessException` → 替换 → 存盘（失败回滚）
- `delete`：按 id 找 → 不存在抛 `BusinessException` → 移除 → 存盘（失败回滚）
- `search`：过滤 `keyword`（匹配 `category` 或 `note`，忽略大小写）+ `type`（为 null 时不过滤）→ 汇总算 `QueryResult`
- `reload`：`repo.load()` → 替换缓存

⚠️ **"先改内存再存盘"必须有回滚**。否则存盘失败后界面显示已删除、重开程序记录又回来了——这是这类作业最常见的失分点。

## 七、作业五条边界要求的落实

| 作业要求 | 落实方式 |
|---|---|
| ① Entry 只表示一条收支记录，余额不入 Entry | 余额只在 `QueryResult` 里现算 |
| ② Entry 提供 `validate()` 做基础校验；跨记录规则由 Service 处理 | `Entry.validate()` 只判自身字段；id 不存在/重复在 Service |
| ③ QueryResult 必须包含完整 List\<Entry\> 及汇总、总收入、总支出、余额 | 五个字段齐全，`count = entries.size()` |
| ④ Service 不得导入 `java.swing`；Repository 不得导入 Swing；View 不得直接 `new FileEntryRepository` | 编译期用 `grep` 检查 import；View 通过 Controller 注入的 Service 引用 |
| ⑤ 异常统一由 Controller 捕获：Validation/Business 显示警告，Storage 显示错误并记日志 | 见第四节 catch 顺序 |

## 八、我标出的 4 处 AI 不合理设计（供你判断）

1. **`ValidationException extends BusinessException` 让异常层级"骗人"** —— 从语义上，输入格式错不是"业务状态不允许"。继承成父子后，调用方一个 `catch (BusinessException)` 就把两者混为一谈，必须靠 catch 顺序硬撑。更清晰的是三者平级（都直接继承 `RuntimeException`）。但作业异常表已定父子，只能按表写，**代价是要在报告里写清"为什么 catch 顺序是契约的一部分"**。
2. **`search` 不声明 `StorageException`** —— 一旦将来有人把"查询也走文件"改成流式读取，签名就得改。这是接口对未来变化的抵抗力不足。
3. **`listAll()` 返回 `List<Entry>` 直接暴露内部缓存** —— 调用方拿到的是 Service 里那个 `ArrayList` 本身，改它等于绕过 Service 改数据（且不落盘）。应该返回 `new ArrayList<>(cache)` 或 `Collections.unmodifiableList`。
4. **`QueryResult` 用无参构造 + setter** —— 可变对象，可能处于"entries 有了、汇总没算"的半成品状态。构造器一次性传入更安全。
