## 二、AI 把我带偏的地方（这部分更值得记）

**1. 它默认代码是"顺利路径"的。**

第一版 `add()` 就是 `cache.add(entry); repository.save(cache);`，两行，看着没问题。但它没想过：`save()` 抛异常怎么办？缓存里已经多了一条，文件里没有——内存和磁盘不一致了，下次 `reload()` 才发现。

**AI 不会主动想"失败会怎样"**，除非你明确要求它处理异常。这是它最系统性的缺陷。

**2. 它给的异常处理是"看起来有"的。**

`catch` 顺序写反、有空 `catch`、`catch` 里只 `printStackTrace` —— 这些代码"能编译、能跑，异常也被接住了"，但它接住了不等于处理了。我如果不逐行看，根本发现不了。

**3. `Math.round(x * 100) / 100.0` 这个写法，是"看起来最标准"的错误答案。**

这个写法在无数教程里出现，它 99% 的情况是对的。错的那 1% 是 `1.005`、`2.675` 这种值。如果我没有写那个"金额正好 1.005"的用例，这个 bug 会一直留在代码里，直到某天汇总金额差一分钱。

**它的危险在于：不像 bug 的地方才最危险。**

**4. 表格排序那个 bug，它甚至没意识到自己踩了坑。**

`table.getSelectedRow()` 拿去 `tableModel.getValueAt()` —— 这行代码在"没有排序器"时完全正确。但它自己在上面一行写了 `setAutoCreateRowSorter(true)`，两者组合起来就是错的。

**AI 能写出每一行都对的代码，但组合起来是错的。**

## 三、我自己补上的判断

| 判断 | 为什么非得自己想 |
|---|---|
| 余额放 `QueryResult` 现算 | AI 说放 Entry 里也行，但"历史记录的余额会变"这个矛盾，只有人能想到 |
| 写盘失败必须回滚缓存 | 这是业务正确性问题，不是语法问题 |
| `load()` 只对"文件不存在"返回空 | "文件损坏"和"还没有文件"混为一谈，会导致覆盖真实数据 |
| CSV 不能用 `split(",")` | 备注里一个逗号就静默错位 |
| 界面层不写自动化测试 | 要判断"值不值"，AI 只会说"应该提高覆盖率" |

最后一条其实最典型：**AI 倾向于"什么都做全"，人要做的是"判断什么不做"。**

## 四、关于测试，我学到的

**1. 测试不是"证明代码对"，是"暴露我没想到的情况"。**

59 个用例里，真正抓到 bug 的只有 1 个（`1.005`）。但剩下 58 个的价值在于：它们让我**被迫想清楚**"这个方法的边界到底在哪"。写 `amountOneCentPasses` 的时候我才意识到"金额 0.01 算不算有效"这个问题，之前没想过。

**2. 用例写得对不对，比写多少个重要。**

`decimalSumDoesNotDrift`（0.1+0.2==0.3）看起来是在测浮点精度，实际上对 `Math.round` 版本的 `round2` 完全无感——因为那个版本处理 0.1+0.2 也是对的。

**同样是"测精度"，测 0.1+0.2 和测 1.005，效果天差地别。**

**3. 注入实验比"测试全绿"更有说服力。**

测试全绿只能说明"当前代码和断言一致"，不能说明"断言真的在管代码"。我把回滚那行注释掉，测试立刻红——这才证明那条用例是活的。

如果注入之后测试还是绿的，那说明这条用例是装饰品。

## 五、如果重做一次

1. **先写异常路径的测试，再写正常路径。** 这次是先写正常路径，异常路径是补的，补的时候才发现 `catch` 顺序、回滚这些坑。
2. **给界面层至少留一个自动化冒烟。** 这次 `ControllerSmoke` 是临时写的，没进仓库。如果进了仓库，每次改完跑一遍，比手工点可靠。
3. **`save()` 的原子替换应该一开始就做。** 这是"想得到就该做"的事，不是"测试发现了才改"。
4. **不要相信"教程里常见的写法"。** `Math.round(x*100)/100.0` 是最典型的例子。

它给的是速度，不是正确性。
